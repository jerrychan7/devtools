# Changelog

All packages share one version and are released together (see DEV.md, "Releasing to npm"). Each release says first which Chrome its DevTools frontend comes from; the versioning rules are in DEV.md too. Changes are listed under `Unreleased` as they land, and moved under the version when it is released. The Chinese version is [CHANGELOG.zh-CN.md](CHANGELOG.zh-CN.md); the two say the same.

## Unreleased

- The accessibility tree no longer uses dom-accessibility-api: roles, the text of labels and the descriptions are computed by the project's own code, compared with Chrome on cases imported from that library's tests and from web-platform-tests. More nodes now get Chrome's role (an invalid first `role` token falls back to the next, and elements such as `del`, `em`, `time`, `abbr` or `canvas` get Chrome's own roles), and names, descriptions, values and properties follow Chrome's rules: every one of the about 1,800 imported cases now matches Chrome, layout tables, image map areas and CSS counters in generated content included. `accessibility.js` grows from about 29 KB to about 40 KB.
- `devtools-anywhere` has no runtime dependencies any more: snapDOM was already built into `dist/snapdom.js` and is now a development dependency, and dom-accessibility-api is gone.

## 0.4.0

Based on Chrome 158 (158.0.8127.37).

- The DevTools frontend now comes from Chrome 158 (it was Chrome 156), with that version's panels and UI; the browser default styles shown in Styles follow Chrome 158 too.
- The Accessibility pane in Elements shows the accessibility tree, and `Accessibility.getPartialAXTree`, `getFullAXTree`, `queryAXTree`, `getRootAXNode`, `getChildAXNodes` and `getAXNodeAndAncestors` answer as in Chrome, for tools and agents reading the page's structure. The tree is computed in the page by `accessibility.js`, loaded next to the bundle on first use; it includes dom-accessibility-api (MIT).
- The Animations panel lists the page's CSS animations, transitions and Web Animations, and pauses, seeks, retimes and changes their speed. It finds them in shadow trees (declarative ones and hosts inserted later included) and in same-origin iframes, names the node of a pseudo-element's animation as Chrome does (a `::backdrop`'s names its dialog instead, as our DOM has no node for it), and keeps two CSS animations started apart in two groups. It also reports the animations `getAnimations()` misses, as Chrome does: without a target, out of the document, over at once or cancelled before their first frame (the probe hooks `animate()`, `new Animation()`, `play()`, `pause()` and `cancel()`). The playback rate follows the rate the page sets and gives it back on disable; dragging the scrubber seeks each animation to its own time, plays a finished one first and stops at its end, as Chrome does. In the frontend, removing the last animation group no longer throws. Scroll-driven animations are listed with their scroll or view timeline, in pixels; the scrubber scrolls the page and follows the page's own scrolling, through isolated worlds (`Page.createIsolatedWorld`) and bindings (`Runtime.addBinding`) simulated in the page. Animations of any pseudo-element (`::backdrop`, `::scroll-marker`, `::column`, view transitions', with pseudo-classes after them too) are grouped by the rules that win their properties, as in Chrome, and view transitions started on an element are seen. The hooks stay out of the page's sight: `startViewTransition` is hooked on the prototypes, by the CSS domain, and given the page's options read once, as a new dictionary whose `update` is wrapped, `reverse()`, `finish()`, `updatePlaybackRate()` and new times or rates are seen too, the panel's controls call the browser's own functions rather than the page's (but a change of timing, made through the effect's `updateTiming()`, which a page's wrapper sees), and the probe's own errors no longer go through a `console.error` the page wrapped.
- Emulation reaches the page's HTML and CSSOM too: a `<picture>`'s `<source>` and the `sizes` of images pick their resource under the media emulation as Chrome does, the `style` attributes of the page's elements get the safe area insets, and rules the page inserts through `insertRule()` or `replaceSync()` are emulated in the same task, those nested in a style rule included. `appendMedium()` and `deleteMedium()` on a media list the emulation rewrote find the entries the page wrote, as in Chrome. The page's attribute values are shown to the client as the page wrote them, and the agent's own writes send no DOM-domain events to the client. An edit of an attribute or a style the emulation rewrote is undone (`DOM.undo`) to the text the page wrote, so it is not left rewritten once the emulation ends. The DOM search by text no longer matches an attribute the agent put on a node and the client is not shown (the marks of a forced pseudo-class state and of forced colors; a search by selector or by XPath that names one still finds the node, see the limitations), and undoing an attribute edit no longer brings back the state that mark had when the edit was made.
- Emulated media features (`prefers-color-scheme`, reduced motion, contrast, forced colors, …) and media type, and vision deficiencies, in the Rendering panel and device mode take effect, by rewriting the media queries of the page's style sheets, `<source>` elements and image `sizes` and the queries `matchMedia()` gets (their change events come in the next frame), and with Chrome's SVG filters. The vision deficiency filter is the backdrop filter of a mask in the top layer, which leaves the page's own `filter` on `<html>` and its computed style alone and stays above dialogs and popovers the page opens later. A `change` listener added to a MediaQueryList with a String object as its type, or with an object that converts to the name, gets the emulation's events, and a listener's options are read once, as the browser reads them. A MediaQueryList whose `change` listeners the browser removed (one added with `once`, or with a signal since aborted, even where the page stops the signal's `abort` event; before Chrome 116 not in that case, see the limitations) is collected, as without the probe.
- Safe area insets (`Emulation.setSafeAreaInsetsOverride`) are read through custom properties the emulation sets on `:root`, so changing them no longer rewrites the page's style sheets: the Styles pane and the style sheet text show the `env()` the page wrote, as Chrome does, and a shorthand with one side the page changes keeps the other sides' insets while the emulation runs, reading the real insets again once it ends. A shorthand with a longhand after it, which the browser reads as empty, is compared by its text: a page's edit of it keeps the page's own value instead of being put back to the `env()` it had, and a change that needs no rewrite keeps the text the browser wrote. A style sheet the page reads while the safe area emulation rewrites it is no longer reported as changed (`CSS.styleSheetChanged`), nor served serialized after the emulation ends (the media emulation may still report a `<style>` whose `@media` rules it rewrites, see the limitations). Names written with CSS escapes are read as Chrome reads them (`e\nv(…)` is `env()`), and a page's text with a comment mark in a string (`content: "/*"`) written over a rewritten one is kept whole. A text the page writes over a rewritten one comes back as the page wrote it once the emulation ends, byte for byte in a style attribute (its comments, empty declarations and last semicolon included), and a custom property whose value leaves a function or a string open keeps its value through the rewrite, and so do the declarations the page sets after it through the CSSOM. A rule with an `!important` declaration before a plain one keeps their order when the insets are emulated, a rule that declares a logical property before its physical counterpart (`padding-inline-start` before `padding-top`), or the reverse, and a `style` attribute the CSSOM wrote that does, keep the order of their declarations too, and the values the cascade gives them, even where the browser's text has written the later longhand into a shorthand (`padding: 1px; padding-inline-start: …; padding-left: 2px`), but for a property with no value to be added again with (`all`, and the sides of a pending shorthand of which another side was set after it, in a block that is not known by what the page wrote it in), which stays where it is (see the limitations), and a declaration the emulation did not change keeps the text the browser serialized. A block that declares a shorthand with `env()` and then a longhand of the same group (`padding: max(env(safe-area-inset-top), 8px) 16px; padding-bottom: 0`), which the browser serializes without the shorthand's text, is emulated from what the page wrote it in through the CSSOM while CSS is enabled or an emulation rewrites the page: the text it was set to and the properties set after it, so an element whose style a framework sets property by property (`el.style.padding = …; el.style.paddingBottom = …`) while the insets are emulated is emulated too. Such a block keeps the order of its declarations, and reads as the page wrote it once the emulation ends; an edit of such a rule in the Styles pane is undone (`DOM.undo`) to the block the page wrote. To follow those writes, the agent proxies the CSSOM's rule list and style map functions from the moment it loads, and, only while CSS is enabled or an emulation rewrites the page, a style's setters and its `setProperty()` and `removeProperty()`, with accessors on `CSSStyleDeclaration.prototype` for the names of a style's properties. A page can tell: `toString()` prints the proxied functions without their name, an error thrown through one has one or two more frames of the bundle, a style's property names are the prototype's and no longer its own properties, and writing a style costs more, the latter two only while those proxies are there (the limitations, under following the page's writes, give the list). Where what the page wrote is not known for sure, the `env()` of such a shorthand is not emulated: the sides the block reads with no value stay as they are, and the rest of the block is rewritten by its own text (see the limitations). Insets are integers in the int32 range, as in Chrome: other values fail with "Invalid parameters".
- Emulation no longer freezes a page whose script puts back an attribute the emulation rewrote each time it changes it: the rewrite waits, longer each time while the page keeps putting it back, in the same task or from tasks of its own. A sheet's own media list (`sheet.media`) the page changes is emulated in the same task, as a rule's media list is. A page's wrappers of the functions the agent calls on its elements, documents and window (the attribute methods and `attributes`, `matches`, `querySelector(All)`, the CSSOM's `insertRule()`, `deleteRule()` and `replaceSync()`, the accessors and methods of style sheets, rules, media lists and declaration blocks the emulation reads and writes (`getPropertyValue()`, `setProperty()`, `removeProperty()` and the like), `adoptedStyleSheets`, `setTimeout`, `queueMicrotask`, `requestAnimationFrame`, `performance.now`, `getComputedStyle`, `MutationObserver`, `addEventListener` and `removeEventListener`), put over them after the probe took them, no longer see the emulation's attribute and CSSOM writes and its scan of forced colors (the elements of the vision deficiency mask are still made and placed through the page's DOM functions), the sheets devtools-anywhere hides, the attribute reads and writes on the copy of a rewritten element (the `cloneNode()` call itself is still seen), the attribute writes of DOM and CSS edits and of their undo, or the emulation's frames, timers and observers. The agent's other calls may still be seen: docs/limitations.md says which calls are kept from the page's wrappers. A page that clears every timer id no longer keeps the emulation's rewrites waiting for good: the turn of its writes ends a second after it began.
- A page script that puts back another spelling of a value the emulation rewrites (`color-scheme:dark` where the emulation writes `color-scheme: dark`, say), or that edits other declarations of a rewritten style attribute (`el.style.transform = …`), no longer makes the emulation write the attribute again and again: the rewrite writes a style attribute only where the values it declares change, and a put-back that changes them waits as for any other put-back. A put-back from a timer the page's observer queues when it sees the emulation's write is an answer in the turn, whichever of the page's observers and the emulation's was made first.
- A page's own write that puts an attribute the emulation rewrote back to a value it had before, such as a `color-scheme` set again, is emulated in the same task, as Chrome does, instead of a frame later.
- An emulated `prefers-color-scheme` reaches `color-scheme` as Chrome's does: a value that names both light and dark (in a style sheet, a style attribute, the CSSOM or a `<meta name="color-scheme">`) takes the emulated scheme, so `light-dark()`, CanvasText and form controls render in it. The root is given no scheme of its own. The Styles pane, the sheet's text and the DOM show the values as the page wrote them, except a sheet the page changed through the CSSOM (see the limitations).
- Emulated media features and media type are kept per client, as Chrome keeps them. A call takes back the features its own client set before, so omitting `features` is the same as `features: []`. A feature another client set stays, unless this client set the same name before: the call takes that name back, even where another client has set it since. The page's media type is that of the last call, whichever client made it; omitting `media` is `media: ''`, which sets none. A client that ends counts as a call with nothing: its features are taken back, and the media type is none, whichever client set it.
- A value Chrome does not read for an emulated feature takes the feature back to its real value, cancelling an earlier value of it; escapes and NUL in feature values are read as CSS reads them, and the feature names given to `setEmulatedMedia` are compared as written, as Chrome compares them.
- Forced colors paint the page with Chrome's palette, the dark or the light one by the emulated or the browser's `prefers-color-scheme`: the system palette's colours on text, links, buttons, fields, marks and selections, and the canvas behind every background (an opaque one hides what it covers, a translucent one keeps its opacity), in the page's frames and shadow roots. Elements that keep their colors (`forced-color-adjust: none`) are left alone, and gradients are taken away where a background has no `url()` image. Form controls are only recoloured, a colour the page sets with `!important` at a higher specificity, or inline with `!important`, keeps its own, and a page that answers the marks by adding elements in the same task, in a microtask or in a timer of no delay has them painted some frames later, while one that answers from a frame callback or a later timer goes on adding at its own pace: see [limitations](docs/limitations.md#forced-colors).
- The Event Listeners pane (`DOMDebugger.getEventListeners`) no longer lists a `once` listener that has run and stopped its event for the listeners after it (`stopImmediatePropagation()`), nor a listener its signal removed where a listener of the page stopped the signal's `abort` event; a `once` listener that has run is no longer kept by its signal until the abort; a listener the page adds again from its own `abort` listener is listed; and elements that listen with a signal the page keeps are collected once the page drops them, as the probe no longer puts an `abort` listener on the page's signal to record an event listener (but for a MediaQueryList's `change` listeners in a browser without `AbortSignal.any`, before Chrome 116: see the limitations; the one it adds for a WebMCP tool registered with a signal is as before).
- Styles shows the browser's "user agent stylesheet" rules, from a copy of Chromium's `html.css` shipped as `chromium-html.css`; the Computed pane refreshes by itself.
- Style sheets are served in the text they were written in (that of a `<style>`, a file fetched again, or what `replace()` and `replaceSync()` got), with Chrome's ranges for selectors, declarations, commented-out properties and at-rule conditions, and edits (`setStyleTexts`, `setRuleSelector`, the new `setMediaText`, `addRule`, `setStyleSheetText`) change it as written, leaving a `<style>`'s text and id alone. Changes the page makes through the CSSOM send `CSS.styleSheetChanged` (a sheet's own media list, `sheet.media`, is the exception, as in Chrome); the text is serialized after them. `getStyleSheetText` of a cross-origin sheet without CORS fails. Matched styles include the `@keyframes` of the element's animations (those of the element's tree scope that apply), and `setKeyframeKey`, `setSupportsText`, `setContainerQueryText`, `setContainerQueryConditionText` and `setScopeText` edit keys and conditions as written. As in Chrome (157): the page's changes are seen also through a style rule's nested `insertRule()` and `deleteRule()`, a rule's media list, `@counter-style` and `@font-feature-values` rules and properties written by name (`rule.style.color = …`, found afterwards), while writes that change nothing (an unknown name, a priority other than `important`) are not counted; headers say `isMutable` once the rules were changed through the CSSOM or by an edit; a commented-out declaration is reported only when it parses; style attributes and styles given a text are read with Chrome's text and ranges, and forgotten once the attribute is removed; custom properties keep `{}` values and escaped names such as `\2d-x`, and declarations after a nested rule the CSSOM drops still count. `setStyleTexts` refuses a text that would not stay the rule's style ("Style text is not valid"), takes every range in the text from before the first edit, and undoes the edits already made when one fails, out of the undo history; `setRuleSelector` and `setMediaText` keep the rule when the new text does not parse. A sheet the page changed before CSS was enabled is sent `CSS.styleSheetChanged` once found changed, a copy of a cross-origin sheet that arrives late no longer overwrites newer text or announces it twice, and rules pair with their text by what tells their selectors apart. The remaining gaps are in [limitations](docs/limitations.md#style-sheet-text).
- Large style sheets are faster: CSS is tokenized and outlined in WebAssembly (inside the bundle, no new file), the page's CSSOM changes and `setStyleSheetText` update only the rules they touch, and sheets are checked and paired with their text while the page is idle. On a 2.6 MB sheet (headless Chrome, one machine) `CSS.enable` takes about 23 ms, and the first `getMatchedStylesForNode` after an idle moment about 200 ms.
- Network: blocked URLs, extra headers, disabling the cache, offline and the user agent override apply to the page's `fetch()` and XHR; the Reporting API's reports the page sees are listed.
- The Application panel's IndexedDB and Cache Storage views refresh on the page's writes, and the Service workers view lists the page's registrations, which it can update and unregister; commands that need the worker itself fail with "Not supported in the page".
- The Layout pane's grid, flex, container query and scroll-snap overlays, isolation mode, device mode's hinge and display cutout, and frame highlights are drawn in the page.
- The Issues panel shows CSP violations, deprecations, quirks mode and form issues; the Console shows `[Violation]` messages for slow handlers and forced reflows.
- `DOM.scrollIntoViewIfNeeded` in a linked cross-origin iframe scrolls the pages holding it too, as in Chrome.
- Shell mode: the Service Worker remembers where each same-origin script's `debugger` statements are, by the hash of its content, so a script loaded again is not parsed again (on a 7 MB bundle, measured in Node: about 5 ms where it is found, against about 80 ms) and an edited one is rewritten anew; `debugger` after `x-->0` on the same line is now found. In the Console, an expression after a `}` on the same line gives its value again, and a method named `catch`, `if` or the like no longer breaks top-level `return` checks.
- Memory: a `<devtools-anywhere>` the page removes, placed by the page or the global one, can be garbage collected with its panel and its frontend iframe; removed elements with a shadow root are collected too, without waiting for an iframe to be added or removed, as the agent's frame registry no longer keeps them alive.
- Opening the panel no longer prints `console.assert` errors in the page's console: the call frames of console messages, uncaught errors and request initiators now carry the id of the script the Sources panel lists for their URL, so their links in the Console and their marks in Sources resolve to that script.
- Under Chrome 158, a click in a cross-origin or sandboxed iframe focuses what it presses again, so keys and text reach the iframe's field: since that version a cross-origin iframe's page can focus an element only while its frame has the focus, and a press now gives its frame the focus first, as Chrome does.
- With the browser's own WebMCP API (Chrome 158), invoking a form's tool with a parameter the form does not have fails with Chrome's text, `Input contains a parameter "…" but there is no such parameter for the tool`, instead of the browser's `Failed to parse tool input arguments.`

### API changes

Public API, as in `packages/*/etc/*.public.api.md`: unchanged since 0.3.0.

- `devtools-anywhere` ships two more files in `dist/`, loaded on first use: `accessibility.js` (exported as `./accessibility.js`, with its source map `accessibility.js.map`) and `chromium-html.css`; self-hosted, serve them with the bundle. `chromium-html.css` is under the LGPL (2.0 or later), the package's only file that is not MIT or BSD; its license ships as `chromium-html.LICENSE.txt`, and leaving both out only drops the user agent stylesheet rules. It depends on `dom-accessibility-api` now.
- The probe grows from 18948 to 27489 bytes minified (raw bytes, not gzip; 25409 before the functions the agent calls on the page were saved with it), mostly for the Animations panel's hooks, the `matchMedia()` hooks, the browser functions saved for them and for the vision deficiency mask, and the functions the agent calls (an internal interface of the probe, not public API).
- In shell mode the Service Worker keeps its `debugger` rewrite record in the Cache API, under `devtools-anywhere-service-worker-rewrites`; it is deleted when a new worker activates, when shell mode ends, and when a page outside shell mode unregisters a left-over shell worker.
- The messages between the probe in a cross-origin iframe and its parent gained the internal event `DevtoolsAnywhere.scrollParent`: use the same version of the probe on both sides.

## 0.3.0

Based on Chrome 156 (156.0.8078.80).

- Same-origin iframes, as in Chrome: Elements expands them; each has its frame in the Page tree and its execution context in the Console's context menu, with its console messages and errors; Styles shows its own sheets and media; Network tags its requests with its frame; highlighting, inspect mode and Input reach into it. Iframes in shadow trees and same-origin `<object>` and `<embed>` documents are frames too; `Page.getResourceTree` lists each frame's own resources. Logs and requests an iframe makes before its load event are missing (except for srcdoc and blank iframes), and its navigations are reported once loaded.
- Cross-origin iframes whose page loads the probe too, when each side trusts the other (`data-frame-origins` in the parent, `data-parent-origins` in the iframe; the Vite options `frameOrigins` and `parentOrigins`): they are child targets, as Chrome's out-of-process iframes, through `Target.setAutoAttach` and messages routed by `sessionId`, in every setup (embedded, shell mode, remote). Elements shows their document under the `<iframe>` (`DOM.getFrameOwner`), the Console their contexts; input over them reaches them, and wheels chain back to the parent. Each client attaching them gets a session of its own, as in Chrome (the page's DevTools and a remote agent at once). Their targets survive navigations, and iframes in them link level by level.
- Sandboxed iframes without `allow-same-origin` (with a `src` of the page's origin, `about:blank` or `srcdoc`) whose document loads the probe, when the parent lists `sandboxed` in `data-frame-origins` and the document the parent's origin in `data-parent-origins`: they are merged into the parent's target, as Chrome keeps them there, with no child target. Elements shows their document under the `<iframe>`, the Console their context and messages, Network their requests, Sources their scripts, Styles their sheets; highlighting, inspect mode and Input reach into them. Off by default; those with a `src` of another origin, same-site too, are still refused. The remaining gaps are in [limitations](docs/limitations.md#sandboxed-iframes).
- `DOM.getNodeForLocation` takes document coordinates, not viewport ones, and `DOM.scrollIntoViewIfNeeded` centers an element that is out of view, as in Chrome. Hovering with `Input.dispatchMouseEvent` sends `pointerout`, `pointerover`, `mouseout`, `mouseover` in Chrome's order.
- `Page.navigatedWithinDocument` for `history.pushState`, `replaceState`, fragment changes and navigations the Navigation API intercepts, in the top page and in frames.
- Requests the page made before the probe ran are reported from Resource Timing (without stack, headers or body), as Chrome reports them too.
- `DOM.requestChildNodes` no longer sends children the client already has, as in Chrome: the frontend asking twice emptied an expanded iframe.
- In shell mode, a reloaded frontend starts a new session, as in Chrome.
- In shell mode, `Emulation.setDeviceMetricsOverride` and `clearDeviceMetricsOverride` work from any client of the page (a remote agent, a `createCdpSession`), not only the shell's frontend: the last override set applies, and a client's clear or end only lifts its own; a remote client's override survives page reloads, re-applied in the order the clients attached, as in Chrome. Their parameters are checked with Chrome's errors; outside shell mode the two commands fail, saying so.
- Commands the page cannot carry out (auto dark mode, turning focus emulation on, the pinch zoom, background services, bypassing the Service Worker, autofill addresses, the security isolation status, browser feature flags, network throttling, enabling domains whose events only the browser has such as the profilers, …) fail with "Not supported in the page: <why>" instead of succeeding without effect or answering with made-up data; `CSS.getEnvironmentVariables` returns the env() values the page resolves; those that could be done in the page still succeed, and are listed in the roadmap.
- An embedded frontend that reloads is told by its command ids starting again, not by its frame's load event, which comes after its first commands: what it enabled at once is no longer ended by the load.
- `CSS.createStyleSheet` fails with "Frame not found" for an unknown `frameId`, as in Chrome.
- Merged sandboxed iframes, as in Chrome: each new document gets new ids, and a reloaded one's execution contexts are destroyed and not reused, while a document linking again keeps its own; DOM undo and redo cover the page and its merged frames in one history, in the order of the edits, CSS edits in the frames included; a frame not answering within 1 s for its document, a node or a point is taken as not answering; `Page.navigate` takes a sandboxed iframe's `frameId`, merged or not; after `Page.disable`, the frames' queued events are no longer sent.

### API changes

Public API, as in `packages/*/etc/*.public.api.md`: additions only, nothing removed, renamed or changed.

- Probe script attributes (`devtools-anywhere`): `data-frame-origins` (origins of cross-origin iframes this page's DevTools debugs, space-separated; `sandboxed` for its sandboxed iframes) and `data-parent-origins` (origins of the pages that may debug this one in their iframe).
- Vite plugin options (`@devtools-anywhere/vite-plugin`): `frameOrigins` and `parentOrigins` (arrays), written into those two attributes.
- CDP: commands the page cannot carry out now fail with -32000 "Not supported in the page: <reason>" instead of succeeding without effect (listed above); `CSS.createStyleSheet` with an unknown `frameId` fails. Other changes to CDP answers and events are behavior fixes towards Chrome, listed above.
- The messages between the probe, the shell and the remote server gained the internal methods `DevtoolsAnywhere.attach` and `DevtoolsAnywhere.metrics`: use the probe and `@devtools-anywhere/remote-server` of the same version.

## 0.2.0

Based on Chrome 156 (156.0.8078.80).

- From jsDelivr or unpkg, the probe needs no other attribute: it loads the frontend of its own version from there, and shell mode works (without the Service Worker). Shell configs from such a CDN are trusted only in the probe's package and the frontend's at that version, no longer anywhere on the CDN. `data-no-panel` goes without the panel: a page from such a CDN only debugged remotely (`data-remote`) needs it, or it now gets a panel too.
- The docked panel is resized with a grip on the middle of its inner edge, on the page's side, in place of the bar across its whole edge: it covers neither DevTools nor more of the page than it shows, and looks the same in and out of shell mode. The undocked window keeps its bar, which moves it.
- Device mode in shell mode, as in Chrome: DevTools lays out the page and itself, the toolbar's device button sizes the page as a device (scaled to fit) and its menu takes screenshots, docked or undocked. It sets the page's size only, not its pixel ratio, user agent or touch input. A grip against the middle of DevTools' edge, on the page's side, resizes them without covering DevTools, larger on touch screens. Outside shell mode the button is still the screencast's.
- `console.table` of objects shows their fields as columns, as in Chrome, instead of a single "Value" column; columns given as an array filter them.
- `Page.captureScreenshot` and `Page.getLayoutMetrics`: screenshots of the viewport, a region or the whole page, rendered by snapDOM and marked `approximate: true`, for tools and agents that drive the page over CDP.

## 0.1.0

Based on Chrome 156 (156.0.8078.80).

First release.
